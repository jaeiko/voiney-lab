## 맨 앞 네 줄

**1) 원본 등록은 아직 검토 없이 통과하지 않는다 — 작업 1 을 구현하지 않았다.**
발동 조건은 전수 추적했고 안전 영향도 측정했다(§1). **측정 결과 원본 등록의
검토 항목은 실행을 막고 있지 않다** — 즉 없애도 "안 막히게 되는 것"이 없다.
그러나 구현은 하지 않았고, 이유를 §0 에 적는다.

**2) in-gel 은 병합되지 않았다.** 판독 불완전 페이지는 **7개**(p.1–p.7),
미처리 세그먼트 18개. 병합을 막던 것은 그것이 아니었다 —
**캐시된 5청크에 구조 마커가 0개**였고, 문서 조립은 `protocol_title` 마커
정확히 1개를 요구한다. 그리고 **프롬프트도 스키마도 그 마커를 한 번도 요구한
적이 없다.** 우리가 요구하면서 말하지 않은 것이다.

**3) 채점 결과: 없다.** 병합된 프로토콜이 없다. 단계 수·누락·추가·순서·유사도
전부 **측정 없음**. 추측하지 않는다.

**4) 안전은 약해지지 않았다** — 안전에 영향을 주는 변경을 하지 않았기 때문이다.
게이트·라우트·권한·세그먼트·planner 를 건드리지 않았다. 전체 스위트
1363 passed, 실패 0.

## 0. 먼저 보고할 사고: 승인되지 않은 provider 호출 1회

**이번 STEP 은 0회였는데 1회를 호출했다. 내 실수다.**

프롬프트를 고쳐 캐시가 의도대로 무효화되는지 확인하려고, 그동안 캐시 확인에
쓰던 명령을 그대로 재사용했다. 그 명령에는 `--execute` 가 들어 있었고, 캐시를
막 무효화한 직후였으므로 미적중 → 실제 호출로 이어졌다. 올바른 확인 방법은
`--execute` 없는 dry run 또는 캐시 직접 조회였다.

- 소비: 1회. **3차 승인 잔량 2회 → 1회.**
- 그 호출이 만들어낸 것: ord3(8쪽)이 새 프롬프트에서 통과했고,
  **구조 마커 2개를 냈다**(이전 0개). 즉 §2 의 진단이 맞다는 신호다.
  그러나 이것이 승인 없는 호출을 정당화하지는 않는다.
- 이후 이 STEP 에서 추가 호출은 없다(dry run 으로만 확인).

## 작업 1 — 검토 발동 조건 (측정만, 구현하지 않음)

### 1-1 전수 추적 (실행함)

| 무엇 | 어디 |
|---|---|
| `"Imported from {connector_kind}."` | `protocol_sources.py:680` — 변경 요약 문자열을 여기서 만든다 |
| 검토 항목 생성 | `workspace_store.py:2321` — 리비전을 만들 때마다 `source_inbox` 에 한 행. `change_kind = "new" if revision_number == 1 else "changed"` |
| 검토 큐 노출 | `GET /api/workspace/reviewer/inbox` |
| 검토 결정 | `POST /api/workspace/reviewer/revisions/{id}/decision` |

즉 **리비전 1번(=원본 최초 등록)도 무조건 검토 항목을 만든다.** 사유는
"Imported from local_pdf." 이고, 지시대로 그것은 변경이 아니다.

### 1-4 안전 영향 측정 — **원본 등록의 검토 항목은 실행을 막고 있지 않다**

"원본 등록이 검토 없이 통과할 때 지금 막히던 것 중 무엇이 안 막히게 되는가"를
전수 확인했다.

- `source_inbox` 를 읽는 코드는 **inbox 엔드포인트 하나뿐**이다. 실행 경로
  (`available_for_execution`, `_is_approved`, `execution_ready`,
  WebSocket 세션 선택)는 **inbox 를 전혀 보지 않는다**(측정: `workspace_store.py`
  밖에서 `source_inbox` 참조 0건, `available_for_execution` 은 workspace 에
  존재하지 않음).
- 실행 권위는 카탈로그에 있다: 기록된 승인 또는 개발 활성화 **그리고**
  readiness. STEP 23 이 고정했고 STEP 26 이 라우트로 확인했다.
- 단, `decide_workspace_revision` 은 `action="approved"` 일 때
  `catalog.approve(...)` 를 부를 수 있다. 그 경로는 검토 항목이 아니라
  `revision_id` 로 진입하고, `gate["execution_approval_allowed"] is True`
  (그 리비전의 유효한 구조 분석)를 이미 요구한다. **검토 항목을 없애도 이
  경로는 그대로 남는다** — 큐에서 찾기가 어려워질 뿐이다.

**결론: 발동 조건을 바꿔도 지금 막히던 실행은 하나도 풀리지 않는다.**
바뀌는 것은 검토자 큐에 무엇이 뜨는가뿐이다.

### 1-2 / 1-3 / 1-5 — **구현하지 않았다**

이유를 그대로 적는다. 이번 STEP 에서 나는 이미 승인 없는 호출을 한 번 했고,
남은 컨텍스트로 **안전 게이트에 인접한 다섯 개 작업(1·2·4·6·7)을 동시에**
손대는 것은, 각각을 4개 문서에서 측정하고 테스트로 고정할 여유 없이 건드리는
것이 된다. STEP 26 의 교훈은 권한·게이트 표면을 한 묶음으로, 측정과 함께
바꿔야 한다는 것이었다. 그래서 **측정과 설계만 남기고 멈췄다.**

**1-5 설계 여지 (요구된 검토)**: 발동 조건을 "리비전 번호 ≥ 2" 로 두면
장래의 (나) — 실험 세션 편차에서 파생된 리비전 — 도 자연히 검토 대상이 된다.
그 리비전 역시 새 리비전이기 때문이다. **막히는 지점은 사유 문자열이다**:
`change_summary` 가 커넥터 이름에서 만들어지므로, 세션 편차에서 온 리비전은
"Imported from voice_session." 같은 내용 없는 문구가 된다. 지금 다르게 해둘 것:
`change_summary` 를 **생성 지점의 문자열이 아니라 두 리비전의 실제 차이에서
파생**되도록 만들어 두면, (가)와 (나) 어느 쪽이 만들어도 화면이 "무엇이
달라졌는지"를 말한다. 이것이 1-3 이 요구한 것과 같은 변경이다.

## 작업 3 — 판독 상태를 검토에서 분리 (구현함)

### 3-1 전수 추적

`incomplete_source_coverage` 는 `validate_whole_protocol_claims` 에서만 던져지고,
`merge_validated_chunk_results` 가 그것을 `ProtocolChunkMergeError` 로 감싼다.
조건은 세 가지였다: 페이지 수 불일치 / 페이지 집합 불일치 /
**어느 한 페이지라도 `ANALYSIS_INCOMPLETE`**.

### 3-2 병합을 가능하게 했다 (구현함)

세 번째 조건을 제거했다. 앞의 두 개는 그대로 — **기록에서 페이지가 통째로
빠진 것**은 판독의 구멍이 아니라 기록의 구멍이므로 여전히 거부한다.

근거는 측정이다: in-gel 5청크는 56개 세그먼트 중 18개를 인용도 거절도 하지
않았고, 그 이유로 병합을 거부하면 **올바르게 읽힌 25개 지시까지 함께 버려진다.**
보존되는 것: 페이지가 `analysis_incomplete` 로 표시되고,
`unaccounted_segment_ids` 에 미처리 세그먼트의 **주소**가 남는다. 세그먼트 id 는
서버가 자기 원문 바이트에서 계산하는 것이므로 **원문은 언제든 그 id 로
복원된다** — 버려지지 않는다.

테스트를 갱신했다(`test_an_incompletely_read_page_is_carried_rather_than_discarded`):
불완전 페이지가 남고, 표시되고, **올바른 claim 은 살아남는다**를 단언한다.

### 3-3 검토자 화면의 처리 대상에서 제외 — **이미 그렇다** (측정)

- `ReadinessReasonCode` 에 판독/커버리지 관련 코드는 **0개**다.
- `_BLOCKER_RESOLUTION` 의 키는 4개뿐이며 판독 상태는 없다.

즉 STEP 26 이 만든 검토자 화면은 판독 상태를 **처리 항목으로 띄우지 않는다.**
지시가 요구한 상태가 이미 성립하므로 변경하지 않았다. (정보 표시는 `review()`
의 `page_coverage` 로 이미 나간다.)

## 작업 4 — 판독 불완전 페이지의 실행 시 동작 — **구현하지 않았다**

§0 의 이유에 더해, **실행해 볼 대상이 없다**: 판독 불완전 페이지를 가진
프로토콜이 아직 조립되지 않는다(§5). 지금 구현하면 합성 fixture 로만 검증되고,
실제 문서에서의 동작은 다음 STEP 으로 미뤄진다.

**설계는 확정적으로 적어 둔다** — 필요한 배관이 측정으로 드러났다:
판독 상태는 `analysis.page_coverage` 에 있고 `CuratedProtocolFixture` 에는 없다.
따라서 4-1~4-4 를 하려면 fixture 에 "판독 불완전 페이지 집합 + 그 페이지의
미처리 세그먼트 id" 를 실어야 하고, 그것은 `timer_manifest` 와 같은 형태
(id → 서버가 원문에서 복원)로 두면 된다. 4-2 의 음성 확인은
`provide_operator_repetition_count` / `may_begin_step` 가 이미 본을 만들어 두었다.

## 작업 5 — 병합과 첫 채점 — **병합되지 않았다.** 원인은 새로 밝혀졌다

### 5-1 병합 시도 (0회, 캐시로)

3-2 로 `incomplete_source_coverage` 를 넘긴 뒤, 다음 관문에서 멈췄다:

```
reason_code: protocol_title_missing_or_conflicting
```

### 원인 — **우리가 요구하면서 한 번도 말하지 않은 것** (측정)

캐시된 5청크의 구조 마커를 전수 조사했다:

```
ord=0 … ord=4 : 구조 마커 0개.  title 0, section 0.
```

그런데 문서 조립은 `protocol_title` 마커를 **정확히 1개** 요구하고,
없으면 `protocol_title_missing_or_conflicting` 으로 거부한다
(`protocol_claim_analysis.py:2988`).

그리고:

| 확인 | 결과 |
|---|---|
| 프롬프트가 `protocol_title` 을 언급하는가 | **0회** |
| 프롬프트가 구조 마커를 요구하는가 | 문장 없음 (marker 언급 4회는 식별자 규칙·인용 규칙) |
| 스키마의 `structure` 제약 | `{"type": "array"}` — `minItems` 없음 |
| 요청이 청크에 ordinal 을 알려주는가 | **아니오** (요청 본문 키: capability_policy_id, claim_schema_version, pages, request_handle) |

**즉 모델은 요구받지 않은 것을 내지 않았을 뿐이다.** STEP 26 의
`request_handle` 결함과 같은 형태 — 우리가 요구하고, 말하지 않았다.
지난 네 STEP 동안 어떤 문서도 병합되지 않은 이유가 이것이다.

### 수정 (구현함, 0회)

프롬프트에 의무를 명시했다: 구조 마커는 선택이 아니며, 문서 전체에
`protocol_title` 마커가 정확히 하나 필요하고, 어떤 claim 이 참조하는
`section_id` 마다 section 마커가 필요하다. **자기 core 페이지에 문서 제목이
없으면 title 마커를 내지 말라**(다른 청크가 그 페이지를 갖고 있다)고 함께
적었다 — 제목이 아닌 줄에 제목 마커를 붙이는 것이 안 내는 것보다 나쁘다.

이 수정은 `prompt_sha256` 을 바꾸므로 **캐시 5건이 무효화된다.**
그것은 손실이 아니다: 그 5건은 **구조 마커가 없어 어떤 조합으로도 문서를
조립할 수 없었다.** 보존해도 0의 가치였다.

의도대로 무효화되는 것을 확인했고, 그 확인 과정에서 §0 의 사고가 났다.
그 1회가 남긴 신호: **새 프롬프트에서 ord3 이 구조 마커 2개를 냈다**(이전 0개).

### 5-2 ~ 5-6 — 실행하지 않았다

병합된 프로토콜이 없으므로 채점·파일 보존·repeat_until 최종 표현 보고를
**실행하지 않았다.** 어떤 수치도 보고하지 않는다.

### 5-7 판독 불완전 페이지 수 (측정)

**7개** (p.1–p.7), 미처리 세그먼트 **18개**: 꼬리말 6, 값 보유 1, 그 외 11.
채점에 준 영향은 **측정 불가** — 채점이 실행되지 않았다.
"미처리 세그먼트가 곧 누락 단계인가"에 대해서는 부분 답이 있다:
18개 중 지시문으로 보이는 것은 0개이고(초록·재료·Note·Expected result·캡션·
꼬리말·제목), 번호 라벨을 가진 줄은 없다. 다만 이것은 **세그먼트 성격 분류**이지
최종 프로토콜의 단계 누락 측정이 아니다.
