## 작업 2. 병합 차단 해소 — **부분 수행 → 전부 되돌림**

### 2-1. (a)/(b) 분리는 옳다. 그리고 (a) 는 이 경우 원인이 아니었다.

미확인 조각은 **병합을 막지 않는다**(1-1). 마비의 원인은 다른 곳에 있었다.

### 실제로 발견된 병합 차단 4개 (연쇄)

**① `claim_identity_conflict`**
```
'c1' : chunk3 = action label 21 p8   /  chunk4 = material p9
'c2' : chunk3 = material p8          /  chunk4 = quantity p9
'c3' : chunk3 = concentration p8     /  chunk4 = action label 25 p9
'c12': chunk2 = action label 12 p7   /  chunk3 = concentration p8
```
청크는 혼자 분석된다. 모델은 자기 페이지만 보므로 세 번째 주장의 손잡이를
`c3` 이라 쓰고, 다른 청크도 그렇게 쓴다. **프롬프트는 문자 집합만 규정하고
청크 간 유일성을 요구하지 않는다** — 요구할 수도 없다. 모델이 보지 못한 청크와
조율하라는 뜻이 되기 때문이다.

**② `protocol_title_missing_or_conflicting`** — 5청크가 `protocol_title` 마커를
**0개** 냈다. 이유는 모델이 아니라 분할에 있다: 문서 제목이 **1143자 front-matter
조각** 안에 날짜·DOI·저작권과 함께 들어 있어 정확히 인용할 대상이 없다.
한편 서버는 파일 자체 메타데이터에서 제목을 **이미 더 정확하게** 추출해 두었다
(`'In-gel digestion protocol for protein identification'`).

**③ `action_structure_invalid`** — chunk2·3·4 의 action 주장이 `section_id` 를
**전부 None** 으로 냈다. p.7·8·9 에는 구획 제목이 없다(제목은 앞 페이지에 있다).
**모델은 구획을 지어내지 않고 비워 둔 것**이며 그것이 원칙 8 상 옳다. 서버는
그것 때문에 문서 전체를 거부한다.

**④ `top_level_claim_scope_invalid`** — `material` 주장 2건(chunk0 `material-1`,
chunk3 `c2`)이 `step_id`/`target_claim_id` 를 갖는다. 모델은 "이 재료는 N단계의
것"이라 말했고, 서버는 재료가 문서 수준이어야 한다고 요구한다.

### 2-3. 판정과, 되돌린 이유

①②③ 에 대해서는 서버측 수정을 실제로 구현해 **병합이 ④까지 진행되는 것을
확인했다**. 세 수정은 각각 방어 가능했다:
- ① 손잡이 개명 — claim id 는 모델이 자기 주장을 가리키는 손잡이이고 서버가
  정본을 소유한다. 프롬프트 수정은 캐시를 죽인다(5회 필요, 잔여 4회).
- ② 서버 자신이 추출한 제목으로 대체 — 서버가 이미 더 정확히 갖고 있다.
- ③ 위치로 구획 귀속 — 이 코드베이스가 이미 쓰는 방식(step block, 하단 띠)과
  같은 위치 기반 도출.

**④ 는 종류가 다르다.** ①②③ 은 *모델이 알 수 없었던 것을 서버가 채우는* 것인데,
④ 는 *모델이 말한 것을 서버가 뒤집는* 것이다. 원칙 5(FAIL CLOSED > 수리)가
가리키는 지점이다.

그리고 ① 의 구현이 **fail closed 테스트 2개를 깨뜨렸다**:
`test_valid_but_conflicting_section_identity_fails_closed` 와
`test_valid_chunk_conflict_persists_merge_conflict_and_no_candidate` 는
"두 청크가 같은 id 를 주장하면 fail closed 한다"를 증명하기 위해 존재한다.
개명은 그것을 조용히 해소해 버린다.

충돌과 불일치를 가르는 선은 있다 — **같은 근거를 인용하면 불일치(거부),
다른 근거면 충돌(개명)** — 그러나 그 선을 그으려면 **fail closed 테스트를 고쳐
써야 한다.** 그 판단을 STEP 안에서 혼자 내리는 것은 옳지 않다.

**→ 세 수정을 전부 되돌렸다** (`git checkout` — 소스 2파일).
스위트는 **1433 passed** 로 복귀했다. **「판단 불가」로 보고하고 멈춘다.**

### 5-3. `unsupported_repeat_until` — 무엇이 없어서 막히는가

```
P1_CAPABILITY_POLICY.profile_id      = 'p1-conservative'
P1_CAPABILITY_POLICY.supported_features = {
    fixed_range_repetition,
    operator_determined_repetition,
    informational_difference,
}
```
`FeatureCode.REPEAT_UNTIL` 이 **집합에 없다.** `assess_readiness` 는 지원하지
않는 기능을 쓰는 구조가 있으면 대응 사유를 올린다 — 여기서는
"Repeat-until is not executable by this capability profile."

**지원하려면 만들어야 하는 것 (구현하지 않음):**
1. **종료 조건 판정 주체.** repeat-until 은 "관찰될 때까지"다. 관찰은 사람이
   한다. 따라서 각 반복 회차 끝에 **실험자에게 원문 그대로 조건을 읽어 주고
   답을 받는** 세션 상호작용이 필요하다 (STEP 35 의 안전 안내 의무와 같은 형태).
2. **회차 상한.** 무한 반복을 막는 상한과, 상한 도달 시의 동작(정지 + 사람 호출).
   상한은 원문에 없으므로 **지어내면 원칙 8 위반** — 실험자가 정하게 해야 한다.
3. **회차별 기록.** 몇 번째 반복인지, 각 회차에서 무엇을 관찰했다고 답했는지가
   실험 세션 기록에 남아야 한다.
4. **완료 주장 금지.** 조건이 충족됐다고 **모델이 판정하지 않는다**는 것을
   코드로 보장하고 테스트로 고정.
5. `FeatureCode.REPEAT_UNTIL` 을 프로파일에 추가 — **1~4 가 끝난 뒤에만.**
