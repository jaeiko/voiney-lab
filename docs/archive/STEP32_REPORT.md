# STEP 32 — 수동 수집의 결과를 읽는다

## 요약 세 줄

1. **캐시에 유효한 청크: 3 / 5** (ord 0, 3, 4 통과 · ord 1, 2 없음).
2. **채점: 실행하지 않음.** 병합은 5청크 전부를 요구한다(`missing_chunk_result`).
   2/5 가 없으므로 단계 수·누락·추가·순서·유사도 어느 것도 산출되지 않았다.
3. **repeat_until 3건: 판정 불가.** 세 문장 중 p.5 와 p.6 은 **ord 1**,
   p.8 은 ord 3 에 속한다. ord 1 이 없으므로 STEP 31 이 고친 "청크 경계를 넘는
   반복 범위"가 실제로 해결됐는지는 **이번 STEP 에서 판정되지 않았다.**

이번 STEP 의 provider 호출: **0회.**

## 작업 1. 캐시 상태 확인

**실행한 것**: 5청크 각각의 키를 현재 계약으로 계산하고 캐시에서 재검증 로드.

### 1-1 / 1-2. 결과

| ord | core pages | 재검증 | claims | markers | 라벨 주장 |
|---|---|---|---|---|---|
| 0 | 1, 2, 3 | **통과** | 7 | 2 | 1, 2 |
| 1 | 4, 5, 6 | **없음** | — | — | — |
| 2 | 7 | **없음** | — | — | — |
| 3 | 8 | **통과** | 12 | 0 | 21, 22, 23, 24 |
| 4 | 9 | **통과** | 3 | 0 | 25 |

디스크의 캐시 항목 14개 중 3개가 현재 키로 조회된다. 나머지 11개는 이전
STEP 의 잔여물로, 새 키(세그먼트 버전 6 + 프롬프트 해시 + `request_sha256`)로는
하나도 조회되지 않는다. 이것은 STEP 31 이 의도한 동작이다.

파일 mtime 상 수집 순서는 ord 0 (11:01:02) → **약 11분 공백** → ord 3 (11:12:10)
→ ord 4 (11:12:20) 였다. 공백은 ord 1·2 시도와 일치하지만, **시도했다는 증거가
디스크에 없다.**

### 1-3. 거부 사유 — **디스크에서 복구 불가**

`diagnose_provider_chunk.py` 는 보고서를 **stdout 으로만** 출력했다. 파일로
남기지 않았다. 따라서 사용자가 받은 거부 사유 코드는 **사용자 터미널에만**
존재하며, 이 저장소에서는 확인할 수 없다.

**추측하지 않는다.** 대신 0회로 측정 가능한 것을 전부 측정했다(작업 3).

**고친 것**: 이제 모든 실행이 보고서를 디스크에 남긴다
(`data/development_cache/provider_diagnostics/`, gitignore 대상).
보고서에 provider 산문이나 protocol 원문은 들어가지 않는다 — 카운트, 식별자,
사유 코드, 지연 시간뿐이며, 문제 세그먼트도 id·index·길이·위치로만 기술된다
(불변 제약 12 확인함).

## 작업 2. 병합과 채점 — **실행하지 않음**

**실행하지 않은 것**: 병합, 채점, 2-3 의 모든 항목, 2-5 의 파일 산출, 2-6, 2-7.
**이유**: 5/5 가 아니다. 부분 병합은 계약상 불가능하며, 억지로 하면 `merge` 가
`missing_chunk_result` 로 거부한다. 우회하지 않았다.

**다만 2-7 에 해당하는 것을 수집된 범위에서 측정했다** — 아래 작업 3 참조.
이것은 채점이 아니라 판독 상태 관측이다.

## 작업 3. 원인 규명

### 3-1. 거부 사유 특정 — **불가능. 근거를 남기지 않았다.**

위 1-3 과 같다. 이 항목은 **성립하지 않았다.**

### 3-2. 계약 문제인가 모델 동작인가 — **측정된 것과 측정되지 않은 것**

거부 코드 없이 단정하지 않는다. 다만 0회로 얻은 증거는 한 방향을 가리킨다.

#### 측정 1 — 실패한 두 청크는 라벨이 가장 많은 두 청크다

| ord | core | **numbered labels** | 세그먼트 | 값 세그먼트 | 요청 KB | 결과 |
|---|---|---|---|---|---|---|
| 0 | 1,2,3 | **2** | 12 | 2 | 4.0 | 통과 |
| 1 | 4,5,6 | **9** | 25 | 8 | 4.0 | **실패** |
| 2 | 7 | **9** | 12 | 6 | 2.3 | **실패** |
| 3 | 8 | **4** | 9 | 5 | 2.4 | 통과 |
| 4 | 9 | **1** | 4 | 1 | 1.8 | 통과 |

통과한 청크의 라벨 수는 1·2·4. 실패한 두 청크는 **각각 9**. 요청 크기는
무관하다(ord 2 는 2.3 KB 로 ord 0 보다 작다). 프롬프트는 *"For each distinct
explicit numbered source action on every core page, emit a distinct action
claim"* 을 요구하고 하나라도 빠지면 `numbered_action_missing` 이다.
현재 청크 계획의 상한은 `max_core_labels_per_chunk = 12` 이므로 9는 상한 아래다.

#### 측정 2 — 모델은 decline 을 **한 번도 쓰지 않았다**

통과한 3청크의 페이지별 계정:

| ord | page | 세그먼트 | 인용 | **거절** | **미계정** |
|---|---|---|---|---|---|
| 0 | 1 | 2 | 0 | **0** | **2** |
| 0 | 2 | 5 | 0 | **0** | **5** |
| 0 | 3 | 5 | 9 | **0** | 1 |
| 3 | 8 | 9 | 12 | **0** | 4 |
| 4 | 9 | 4 | 3 | **0** | 2 |

`declined_segment_ids` 가 **전부 비어 있다.** 계약은 "인용하거나 거절하거나,
둘 다도 아니고 둘 다 아님도 아니다"를 요구하는데, 모델은 세 번째 길 —
**아무 말도 하지 않기** — 를 골랐고, 그러면 그 페이지가 `analysis_incomplete`
가 될 뿐 청크는 거부되지 않는다(STEP 28 에서 veto 를 푼 결과).

수집된 5페이지 전부가 `analysis_incomplete` 이고, 미계정 세그먼트는 **14개**다.
p.1 과 p.2 는 인용도 거절도 0 — 모델이 그 페이지에 대해 아무것도 하지 않았다.

#### 판정

- **계약이 길을 막아서 실패한 것은 아니다.** 모순 탐지를 다시 돌린 결과
  4문서 600 substantive 세그먼트 중 **막힌 것 0건**이고, 청크별로 쪼개 봐도
  ord 1 · ord 2 각각 **0건**이다. 세 가지 처분(거절 / 감싸는 단계에 인용 /
  document-level 인용) 중 최소 하나는 모든 세그먼트에서 열려 있다.
- **가설(확정 아님)**: 라벨 9개를 하나도 빠뜨리지 않고 action claim 으로
  내는 것이 실제 실패 지점이다. 통과 사례가 1·2·4 라벨, 실패 사례가 9·9 라는
  분포와, 모델이 decline 을 전혀 쓰지 않고 미계정으로 흘려보내는 관측이
  이 방향과 일치한다.
- **이 가설은 거부 코드 없이는 확정되지 않는다.** `numbered_action_missing`
  인지 `coverage_mismatch` 인지 `declined_segment_states_a_value` 인지에 따라
  대응이 전혀 다르다. **추측으로 계약을 바꾸지 않았다.**

### 3-3. 계약 감사와 모순 탐지 재실행 — 통과

- 계약 감사: **15 passed, 24 subtests**
- 모순 탐지: 4문서 600 세그먼트 중 막힌 것 **0건** (STEP 30 문구로는 347건)
- 전체 스위트: **1409 passed, 1201 subtests**

### 3-4. 고친 것과 잔여 호출 수

**고친 것**: 진단 보고서를 디스크에 남기게 했다. 계약은 **바꾸지 않았다** —
바꿀 근거가 없다.

**필요한 잔여 호출: 2회** (ord 1, ord 2). 통과분 3개는 캐시에서 무료다.
그 2회를 쓰면 거부 코드가 이번에는 파일로 남는다.

## 작업 4. 실행 권한 문제 정리

### 4-1. 차단된 명령 형태

```
timeout 900 python scripts/diagnose_provider_chunk.py <pdf> \
  --chunk 0 --budget 1 --execute
```
→ `Permission denied by the auto mode classifier` (`Blocked by classifier`)

**차단되지 않는 것** (이번 STEP 에서 실제로 실행해 확인):
- 같은 스크립트의 **dry run** (`--execute` 없음) — 2회 실행, 정상 동작
- 서버 기동, `curl`, `pytest`, 파일 편집

### 4-2. 정상 경로 탐색 — **완료하지 못했다**

어떤 형태가 통과하는지 알아내려면 `--execute` 가 든 명령을 실제로 실행해
봐야 한다. **이번 STEP 은 호출 0회이므로 그것을 하지 않았다** (불변 제약 11).
따라서 "이 형태면 통과한다"고 말할 수 있는 것이 없다. **추측하지 않는다.**

이 항목은 **성립하지 않았다** — 조사 자체가 이번 STEP 의 제약과 충돌한다.

### 4-3. 표준 절차 문서화 + 스크립트 — 완료

`scripts/collect_chunks.sh` 를 만들었다.

```bash
scripts/collect_chunks.sh data/runtime/candidate-a-source/in-gel-digestion.pdf 1 2
```

- 청크를 **한 번에 하나씩** 보낸다 (`--budget 1`)
- **첫 거부에서 멈춘다** — 같은 실수로 남은 예산을 태우지 않는다
- 매 실행이 보고서를 `data/development_cache/provider_diagnostics/` 에 남긴다
- 이미 통과한 청크는 캐시에서 무료이므로, 고친 뒤 다시 돌려도 **실패한 것만**
  지불한다
- 인자를 안 주면 `0 1 2 3 4` 를 돈다

**사용자가 할 수 있는 두 가지 정상 경로:**
1. 프롬프트에 `!` 를 붙여 직접 실행 —
   `! scripts/collect_chunks.sh data/runtime/candidate-a-source/in-gel-digestion.pdf 1 2`
2. Bash 권한 규칙을 추가해 이 스크립트를 허용 (현재 `.claude/settings.json`
   과 `settings.local.json` 둘 다 없다). **권한을 스스로 넓히지 않았다 —
   그것은 사용자의 결정이다.**

### 5-3. 측정 결과

| 확인 | 결과 |
|---|---|
| 원본 PDF 등록 → 검토 요청 | **0건** (검토자 inbox 비어 있음) |
| 원본이 목록에 뜨는가 | **뜬다** (`protocol-63d81102…`) |
| 그런데 실행은 막히는가 | **막힌다** (`available_for_execution: false`) |
| 같은 파일명·다른 바이트 → 검토 요청 | **1건** |
| — 종류 | `protocol_revision` |
| — 비교 기준 | `revision-d24cbdb52bac…` (명시됨) |
| — 사유 | `Source changed from 63d81102fb64 to 2bf102779364; review required.` |
| 동일 바이트 재등록 | `deduplicated: true`, 검토 요청 **여전히 1건** |

**작업 6(검토 발동 조건)은 화면에서 실제로 작동한다.**

### ⚠ 내 지시 중 성립하지 않은 것 — 작업 7 은 화면에 아직 닿지 않았다

지시문은 "STEP 31 의 작업 6·7 로 화면 동작이 바뀌었다"고 전제하지만,
**작업 7 은 화면 동작을 바꾸지 않았다.**

`assess_readiness(..., source_lineage=...)` 를 추가하고 기본값을 `UNKNOWN`
(= 수정본과 동일하게 fail closed)으로 두었는데, **`source_lineage` 를 넘기는
프로덕션 호출자가 아직 하나도 없다.** 확인:

```
grep -rn "source_lineage" src/ | grep -v experiment_protocol.py   → 0건
```

따라서 등록된 원본도 여전히 `no_declared_safety_warnings` 게이트를 받는다.
도메인 계층과 세션 계층의 변경은 들어가 있고 테스트로 고정돼 있으나
(`tests/test_safety_disclosure_duty.py`, 11 passed), **카탈로그가 lineage 를
판정해 넘기는 부분이 없다.**

이것은 누락이지 실수의 은폐가 아니다 — 기본값이 엄격한 쪽이므로 **안전이
약해진 상태로 방치된 것은 아니다.** 다만 연결하려면 결정이 필요하다:
카탈로그 엔트리(`protocol_catalog`)와 워크스페이스 리비전 계보
(`protocol_lineage_revisions`)는 서로 다른 저장소이고, 카탈로그 엔트리만 보고
"이것이 원본인가"를 알 수 없다. **불명확하므로 fail closed 로 두고 보고한다**
(불변 제약 7).

### 5-1. 사용자가 브라우저에서 확인할 절차

**준비**
```bash
scripts/run_candidate_a.sh          # http://127.0.0.1:8000
```

**절차 A — 원본 등록은 이제 검토를 부르지 않는다**
1. 브라우저에서 `http://127.0.0.1:8000` 을 연다.
2. 프로토콜 업로드 영역에서 PDF 를 하나 등록한다.
3. **검토자 화면**의 "검토가 필요한 요청" 목록을 본다.
   - **정상**: 방금 등록한 문서가 **나타나지 않는다.**
     목록이 비어 있으면 "대기 중인 검토 요청이 없습니다. 원본 문서 등록은
     변경이 아니므로 검토 요청을 만들지 않습니다." 가 보인다.
   - 예전에는 여기에 "신규 · … · 변경 이유: Imported from local_pdf" 가 떴다.
4. 프로토콜 목록으로 돌아간다.
   - **정상**: 등록한 문서가 목록에 **보인다.**
   - **정상**: 실행 버튼은 여전히 열리지 않는다 (분석·준비도 미충족).

**절차 B — 변경은 여전히 검토를 부르고, 무엇에 대한 변경인지 말한다**
5. **같은 파일명**으로 **내용이 다른** PDF 를 등록한다.
6. 검토자 화면을 새로고침한다.
   - **정상**: 항목이 **하나** 나타난다.
   - **정상**: 제목이 `리비전 변경 · <문서명> · v2` 로 보인다
     (랩 적응본이면 `랩 적응본 · …`).
   - **정상**: 부제에 `비교 기준: <리비전 id>` 와
     `변경 이유: Source changed from … to …; review required.` 가 보인다.
   - **정상**: "검토하기" 를 누르면 diff 화면이 열린다.
7. **같은 바이트**를 한 번 더 등록한다.
   - **정상**: 검토 요청이 **늘지 않는다** (중복은 변경이 아니다).

**절차 C — 안전 경고 (아직 화면에서 확인할 것이 없다)**
8. 위 "성립하지 않은 것"에 적은 대로, 안전 게이트 변경은 아직 카탈로그에
   연결되지 않았다. 등록된 원본은 여전히 안전 게이트를 받는다.
   **화면에서 달라진 점은 없으며, 확인할 절차도 없다.**
