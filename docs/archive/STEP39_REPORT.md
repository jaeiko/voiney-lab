## 작업 1. 무근거 귀속 차단 — **미구현. 원인이 다른 곳에 있다.**

### 1-1. 재측정 (현재 코드, 4문서)

| 문서 | 단계 내부 값 조각 | 라벨을 담은 조각 | 그 뒤의 조각 |
|---|---|---|---|
| in-gel | 20 | 14 | 6 |
| headspace | 21 | 16 | 5 |
| intracellular | 12 | 4 | 8 |
| ANKOM | 34 | 24 | 10 |
| **합계** | **87** | **58** | **29** |

**STEP 34 와 동일하다.** 변동 없음.

### 1-2. 제안 규칙의 실제 효과 — **관측된 2건을 0건 잡는다**

원문을 열어 보니 문제의 값이 **라벨을 담은 조각 자체 안에** 있었다.

```
p.8 seg6: '23 Incubate overnight at 37C 800 rpm, 37°C, 16:00:00\nExtract tryptic peptides 30m\n'
p.8 seg7: '24 Quickly spin down ... which will contain the\n16h\n30m\n'
```

두 조각 모두 **자기 단계의 라벨을 담고 있다.** 따라서
「값 주장의 근거 조각이 단계 N 의 라벨을 담은 블록 안에 있어야 한다」는 규칙은
- **이미 강제되고 있다** (`_within_target_step_block`)
- 이 두 사례에서 **조건을 만족한다** → **잡지 못한다**
- 새로 잡는 건수 **0**, 오탐 **0** → **no-op**

### 왜 p.7 은 분리되고 p.8 은 붙었는가

```
p.7 seg9 : '20 Remove and discard the acetonitrile. ... appearance\nwhen dry.\n'   ← 종결부호 있음
p.7 seg10: '1h\n45m\n10m\n15m\n'                                                  ← 별도 조각
p.8 seg6 : '23 ... 37°C, 16:00:00\nExtract tryptic peptides 30m\n'                 ← 종결부호 없음 → 붙음
```

`_bounded_action_block_boundaries` 는 **번호 라벨과 문장 종결부호**에서만 끊는다.
`16:00:00` 이나 `contain the` 뒤에는 종결부호가 없으므로 **다음 구획 제목이 그대로
붙는다.** 이것이 근본 원인이다.

### 1-3 ~ 1-5. 처분 — **구현하지 않았다**

- 강등 처분을 붙일 대상이 없다. **귀속 결정 자체가 일어나지 않았다** — 모델은
  올바른 조각을 인용했고, 그 조각이 남의 텍스트를 담고 있었다.
- 고치려면 조각 경계 규칙을 바꿔야 하고, 그러면 STEP 31 이 만든 구성 지문
  테스트가 발동하며 **`EVIDENCE_SEGMENT_VERSION` 6 → 7** 이 된다.
- 그러면 **캐시 5청크 전부 사망 → 재수집 5회 필요, 잔여 4회.**
- **이번 STEP 의 지시대로 구현하지 않고 보고한다.**

### 실제 피해는 무엇인가 (정확히)

`instruction_source_text` 가 오염된다:
```
step 23: '23 Incubate overnight at 37C 800 rpm, 37°C, 16:00:00\nExtract tryptic peptides 30m\n'
step 24: '24 Quickly spin down ... will contain the\n16h\n30m\n'
```
에이전트가 24단계를 읽어 줄 때 **「…will contain the 16h 30m」까지 읽는다.**
값이 지어내진 것은 아니지만 **남의 구획 소요시간이 지시문에 섞여 나간다.**

## ⚠ STEP 38 정정 2건

### 정정 1: 24단계는 duration 을 주장하지 않는다

병합 결과 실측 — p.8 의 24단계 관련 주장 전체:
```
c11 quantity target=c10   '24 Quickly spin down the digest ...'
```
**duration 주장 0건.** 채점기 출력에도 그렇게 나온다:
```
step 24 claimed: {'volumes': 1}
step 23 claimed: {'durations': 1, 'temperatures': 1}
```

57600s 는 `protocol_extraction_accuracy._values()` 가 **단계 텍스트에서 숫자를
읽은 결과**다(`_step_text` → 정규식). 추출이 「16시간」이라고 **주장한 적이 없다.**

**고쳤다**: 채점기가 이제 **주장된 값**(`values_claimed`)을 텍스트 파생 값과
**나란히** 보고한다. 기존 지표를 제거하지 않았다 — 그것은 실험자가 듣게 될
텍스트이므로 의미가 있고, **둘이 어긋나는 것 자체가 발견**이다.

### 정정 2: 원칙 8 위반이 아니다

「16h 30m」은 **문서에 있는 값**이다(다음 구획의 소요시간 추정). 지어낸 것이
아니므로 **「문서에 없는 완료 기준을 만들었다」는 내 STEP 38 서술은 틀렸다.**
결함의 종류는 **귀속(attribution)**이며, 이것을 정확히 말하는 것이 중요하다 —
지어냄과 잘못 붙임은 대응이 다르다.

## 작업 2. 반복 누락 탐지 — **구현했다**

### 2-1 / 2-2. `explicit_repeat_instructions` / `uncaptured_repeat_instructions`

- **모양만** 본다: `repeat` … `step(s)` … 두 숫자 + 하이픈/대시/`to`.
  대소문자·`-`·`–`·`—`·`step`/`steps` 변형 처리. 역순 범위는 버린다.
- 서버 자신의 페이지 텍스트에서 읽는다 → **문서가 말한 것**이지 분석의 의견이 아니다.
- 대조는 **인용 조각 + 선언 범위**로 한다. 대응 주장이 없으면
  **`SOURCE_STATES_AN_UNCAPTURED_REPETITION`** readiness 사유를 올린다.
- 검토자가 `acknowledge_gate` 로 해소할 수 있다.

### 2-3. 원칙 8 위반 없음 — 서술과 테스트로 확인

반복 구조를 **만들지 않고**, 범위를 **추론하지 않고**, 단계에 **붙이지 않고**,
반복이 끝났다고 **판정하지 않는다.** 보고하는 범위는 **문서가 인쇄한 그 범위**다
(p.8 은 조건이 확인하는 상태를 19–20 이 만드는데도 **17-18 을 그대로 보고**한다 —
그 불일치는 문서의 것이다). 테스트가 두 함수 본문에 `RepeatUntil` /
`FixedRangeRepetition` / `OperatorDeterminedRepetition` / `steps_by_label` 이
등장하지 않음을 확인한다.

### p.8 은 **어떤 경로로도 반복 구조가 될 수 없다** — 새로 찾은 결함

1. **action 을 target 으로**: 그 조각은 페이지 8 의 **어떤 단계 블록에도 속하지
   않는다**(첫 조각). `action_claim_scope_conflict` 가 `_within_target_step_block`
   을 요구하므로 불가. 7쪽의 20단계를 겨누는 것도 **같은 페이지 요구**로 불가.
2. **document-level 로**: 검증은 통과한다. 그런데 조립에서
   `global_conditions` 로 분류되어 **`BeforeStartPrerequisite` 로 강등**된다
   (`protocol_claim_analysis.py` 4055–4078행). **범위 17-18 은 버려진다.**

즉 **검증이 받아들이는 주장을 조립이 표현할 수 없다.** 그리고 강등 결과가
「before-start 안내문」이라 **처리된 것처럼 보인다.**

### 4-4. 수정안 — **프롬프트가 아니라 조립을 고치면 된다 (0회)**

문서 수준 반복 주장을 `BeforeStartPrerequisite` 가 아니라 **문서 수준 반복
구조**로 표현하면 된다. **프롬프트를 건드리지 않으므로 재수집이 필요 없다.**

단 **그것만으로 p.8 의 반복이 되살아나지는 않는다** — 현재 모델이 그 조각에
대해 아무 주장도 내지 않았기 때문이다(chunk3 인용 0건). 조립 수정은 **덫을
없애는 것**이고, 안전상 중요한 부분은 **작업 2 의 탐지기가 이미 막고 있다.**

**구현하지 않았다.** (프롬프트 수정이 필요하다고 판단되면 재수집 5회 > 잔여 4회
이므로 불가라는 점도 함께 기록한다.)

## 작업 5-B. 반복 구간의 사람 주도 실행(L1) — 설계안

### 5B-1. 세 수준

| | 정의 | 현재 코드 기준 |
|---|---|---|
| **L0** | 반복이 있으면 실행 차단 | **현재 상태.** `FeatureCode.REPEAT_UNTIL` 이 `P1_CAPABILITY_POLICY.supported_features` 에 없어 `unsupported_repeat_until` 발생 |
| **L1** | 반복 구간을 「사람 주도 구간」으로 표시. 에이전트는 **범위와 원문만 읽고 손을 뗀다.** 사람이 완료를 선언해야 진행 | 미구현 |
| **L2** | 회차별 안내 + 타이머, 매 회차 종료 시 질의 | 미구현 |

### 5B-2. L1 은 **지금 데이터로 구현 가능하다**

필요한 것: **반복 범위**와 **그 범위의 단계들**. 둘 다 이미 있다 —
`RepeatUntil.repeated_step_ids` 가 `('step-2' … 'step-7')` 로 전부 담고 있고
(STEP 31 확인), `condition_source_text` 와 `evidence` 도 있다.
**새로 계산할 것이 없다.**

### 5B-3. L1 에서 에이전트가 하는 발화 — 전부

| # | 발화 | 근거 |
|---|---|---|
| 1 | 「여기서부터 N–M 단계는 반복 구간입니다.」 | 범위는 서버가 소유한 구조 |
| 2 | 원문 조건 문장을 **그대로** 읽는다: 「7 Repeat steps 2-7 until the gel band is fully destained.」 | `condition_source_text` — 문서의 문장 |
| 3 | 「반복 구간의 단계는 N, N+1, …, M 입니다.」 | 라벨 나열 |
| 4 | 「이 구간을 언제 끝낼지는 원문 조건을 보고 판단해 주세요. 끝나면 말씀해 주세요.」 | 판단 주체를 사람으로 명시 |
| 5 | 사람의 완료 선언 후: 「반복 구간 종료로 기록했습니다. 다음은 M+1 단계입니다.」 | 기록 사실의 보고 |

**금지 발화** (설계에서 배제):
- 「충분히 하셨습니다」 / 「이제 넘어가셔도 됩니다」 → **완료 판단**
- 「보통 2–3회 하면 됩니다」 → **원문에 없는 횟수**
- 「밴드가 탈색된 것 같습니다」 → **관찰 대행**
- 회차 수 안내 (「3회째입니다」) → 서버가 세지 않으므로 말할 수 없다

발화 1·3·5 는 서버 소유 구조의 진술, 2 는 문서 원문 낭독, 4 는 판단 주체 명시.
**원문에 없는 완료 기준을 말하는 발화가 없다.**

### 5B-4. 서버가 기록할 것

| 항목 | 값 |
|---|---|
| 반복 구간 진입 시각 | 서버 시계 |
| 사람의 완료 선언 시각 | 서버 시계 |
| 선언 주체 | `actor_principal_id` + `actor_role` |
| 대상 구간 | `repetition_id`, `repeated_step_ids` |

**회차 수는 기록하지 않는다.** 에이전트가 세지 않으므로 추정치가 되고, 추정치를
실험 기록에 남기는 것은 이 시스템이 해서는 안 되는 일이다.

### 5B-5. L1 도입 시 `unsupported_repeat_until` 이 해소되는가 — **조건부로 그렇다**

`FeatureCode.REPEAT_UNTIL` 을 지원 집합에 넣으면 그 사유는 사라진다. 그러면
in-gel 에 남는 것은 **(가) 검토자 해소 4건**뿐이고, 검토자가 그것을 처리하고
승인하면 **실행 가능이 된다.**

**단 조건이 있다**: L1 이 실제로 구현되기 **전에** 능력 집합에 넣으면, 지원한다고
선언만 하고 실행 경로가 없는 상태가 된다. **집합 추가는 5B-3·5B-4 가 구현되고
테스트된 뒤에만.**

### 5B-6. 못 잡은 구간(8-9, 17-18)의 처리

L1 으로 안내할 수 없다 — 구조가 없으므로 범위도 단계 목록도 없다.
**최소 요건 그대로 처리한다**: 에이전트가 그 구간을 **반복으로 안내하지 않고**,
`source_states_an_uncaptured_repetition`(작업 2)이 **실행 자체를 막는다.**
검토자가 해소하면 실행은 열리지만 그 구간은 **한 번만 안내**된다. 따라서
해소 화면에 「이 반복은 시스템이 잡지 못했으므로 안내되지 않습니다」가 표시되어야
한다 — 그것이 없으면 검토자가 무엇을 승인하는지 모른다. **미구현 항목으로 남긴다.**

### 5B-7. **구현하지 않았다.** 사용자 결정 `[        ]` 이 비어 있다.

## 작업 6. headspace 투입 비용

### 6-1. 이번 변경이 headspace 에서 어떻게 작동하는가 (오프라인 점검)

- **작업 2 탐지기**: 5건을 찾고, 오프라인 모델이 잡은 2건은 올리지 않는다.
  실제 provider 응답에서도 같은 방식으로 작동한다(문서만 읽으므로).
- **작업 1**: 미구현이므로 변화 없음. 단 headspace 의 **「그 뒤의 조각」 5건**이
  같은 위험군이다.

### 6-2. 필요 호출 수: **8회** (16쪽 → 8청크). 잔여 4회 → **추가 승인 4회 필요.**

### 6-3. in-gel 결함의 headspace 재발 예측과 우선순위

| 결함 | 재발 예측 | 근거 |
|---|---|---|
| **조각 융합 (구획 제목 흡수)** | **재발 가능성 높음** | headspace 단계 내부 값 조각 21개 중 **5개가 「그 뒤의 조각」** |
| **반복 누락** | **재발 가능성 높음** | 문서가 반복을 **5건** 말한다. in-gel(3건)보다 많다 |
| 청크 간 id 겹침 | **재발 확실** | 청크가 8개 → 겹침 기회가 in-gel(5개)보다 많다. **이미 해소됨** |
| 구획 미선언 (이어받기) | 재발 가능 | 8청크 중 다수가 구획 제목 없는 페이지 |
| `unsupported_repeat_until` | **재발 안 함** | headspace 의 반복은 「twice more」 등 **횟수 명시형**이 있어 `fixed_range_repetition` 가능 |

**먼저 고쳐야 하는 것**: 조각 융합(작업 1)이다. 재수집 5회가 필요하므로,
**headspace 수집 전에 처리하는 것이 맞다** — headspace 를 8회로 수집한 뒤 조각
분할을 고치면 **그 8회도 함께 무효가 된다.**

**권고 순서**: ① 조각 융합 수정 + in-gel 재수집(5회) → ② headspace(8회).
합계 **13회**, 추가 승인 **9회** 필요.
