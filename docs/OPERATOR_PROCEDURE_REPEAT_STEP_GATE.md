# 반복 단계 게이트 · 사용자 절차 1장

**서버 기동 → 검토자 해소 → 연구자 선택 → 음성 진행 → 7단계 게이트 → 관찰 발화
→ 전진**까지 한 장. 발화·버튼 문구와 식별자는 모두 코드에서 측정한 실제 값이다.

> **상태 (2026-09-07).** in-gel 은 **선택 가능하다.** `REPEAT_UNTIL` 이 P1 지원
> 기능으로 선언되어 `unsupported_repeat_until` 3건이 사라졌고, 남은 차단 사유
> 2건은 모두 검토자가 해소할 수 있다. 실행 벽은 2단계를 **끝까지** 밟았을 때만
> 내려간다 — 하나만 해소하면 내려가지 않는다.
>
> 반복 단계(7·9·20)의 게이트는 그와 **별개로 그대로 서 있다.** 그것은 readiness
> 가 아니라 실행 시점의 의무이고, 검토자가 아니라 실험자만 해소한다.

---

## 0. 두 종류의 항목을 먼저 구분한다 — 여기서 틀리면 전부 헛수고다

카탈로그에는 이름이 같아 보이는 두 항목이 동시에 있을 수 있다. **구분 기준은
`protocol_id` 하나뿐이다.** 버전 문자열은 둘 다 `pdf-1-analysis-N` 형태가 되므로
구분에 쓸 수 없다.

| | fixture 항목 (**이것을 해소해야 한다**) | 업로드한 PDF(local_pdf) 항목 |
| --- | --- | --- |
| `protocol_id` | `candidate-a-curated-development-v1` | `protocol-<PDF sha256 앞 32자>` (예: `protocol-63d81102fb644fca21e1c2296b566987`) |
| 만들어지는 경로 | `scripts/run_candidate_a.sh` 의 `bootstrap_development_fixture` | 화면의 `새 프로토콜 PDF 등록` (`POST /api/protocols`) |
| 음성 세션이 실행하는 것 | **예** | 아니오 |
| 검토 화면 버전 표기 | `pdf-1-analysis-N` | `pdf-1-analysis-N` (같은 모양) |
| fixture 자체 지문 | `fixture-69517f0fe629d0e4dc35` (감사 답변·provenance 에만 등장, **검토 엔드포인트가 받는 값이 아니다**) | 없음 |

같은 PDF를 업로드했다면 제목과 파일명까지 같다. 검토 화면의 기술 세부(`요청자 ·
원본 출처`)를 펼쳐 `protocol_id` 를 확인하고 `candidate-a-curated-development-v1`
인 항목에서만 작업한다. `protocol-…` 항목을 승인해도 fixture 는 조금도 변하지
않는다.

> **선언 직후 1회 주의.** 이 선언은 fixture 바이트를 바꾸지 않았지만 저장되는
> 분석(readiness)을 바꾸므로, 서버가 기동할 때 **새 analysis 리비전이 append**
> 된다(파일럿 카탈로그는 analysis 4 → 5). 검토자 소견은 기록된 analysis 리비전에
> 귀속되므로 **선언 이전에 해 둔 확인·해소는 새 리비전에 이어지지 않는다.**
> 아래 2단계를 다시 한 번 밟아야 한다. 이전 리비전과 그 소견은 지워지지 않고
> 그대로 남는다.

## 1. 서버 기동

```bash
./scripts/run_candidate_a.sh
```

**보여야 하는 것** — `[OK] LOAD_OK`, `protocol_id: candidate-a-curated-development-v1`,
`revision_id: fixture-69517f0fe629d0e4dc35`, `steps: 25`,
`materialized: existing`(또는 `created`). 여기서 `DuplicateProtocolIdentifierError`
가 나오면 기동이 멈춘다 — 그 경로는 이 선언과 함께 닫혔으니, 나오면 보고 대상이다.

그 다음 `http://127.0.0.1:8000` 을 연다.

## 2. 검토자 해소 — 정확히 두 항목, 이 순서로

검토 화면(`프로토콜 검토`)에서 `검토 목록 새로고침` → `검토 필요` 목록에서
**`protocol_id` 가 `candidate-a-curated-development-v1` 인 항목**을 선택한다.
`아직 해결되지 않은 위험` 블록에 정확히 두 줄이 뜬다.

**① `unresolved_ambiguity · p.8`**

1. 그 줄 아래 안내를 읽는다: "어느 진술이 정본인지 적고, 그 판단의 근거가 된
   원문 세그먼트를 선택해 주세요. 근거 없는 해소는 서버가 거부합니다."
2. 정본 판단 select 에서 **`single_statement_is_authoritative · 이 판단이
   사유를 해제합니다`** 를 고른다. 다른 선택지는 기록만 되고 해제하지 않는다.
3. 근거 체크박스에서 **최소 1개**를 고른다. 8쪽에서 서버가 제시하는 후보는 9개이고,
   이 모호성(`candidate-a-step-20-repeat-range`)의 근거는 맨 위 항목
   `Expected result The gel should look white (dehydrated) …` 이다.
4. **`이 모호성을 해소`** 를 누른다.

**② `no_declared_safety_warnings`**

5. **`안전 경고 확인 처리`** 를 누른다.

**③ 활성화**

6. 프로토콜 검토 패널의 **`데모·연구용 초안 활성화`** 를 누른다.
   (`POST /api/protocols/{id}/activate-development`)

**보여야 하는 것** — ①② 각각 처리 후 해당 줄 끝에 `· 확인됨` 이 붙는다. 두 줄이
모두 확인됨이 되어야 `readiness_gates_cleared` 가 참이 된다. ③ 성공 시
`개발용 초안 활성화 완료 · 최종 승인 리비전은 아닙니다.` 순서는 ①②를 바꿔도
되지만 **③은 반드시 마지막**이다. 활성화는 readiness 를 해제하지 않는다.

## 3. 연구자 선택

`실행할 프로토콜` 드롭다운(`#protocol-id`)에서 `In-gel digestion protocol for
protein identification · …` 을 고른다.

**보여야 하는 것** — 실행 불가 항목은 선택 자체가 막혀 있다(`disabled`). 항목이
회색이면 2단계가 덜 끝난 것이다. 선택되면 실험 컨텍스트에 제목과 리비전이 뜨고
`프로토콜 시작` 버튼이 활성화된다.

## 4. 음성 진행

| 사용자 발화 | 에이전트 |
| --- | --- |
| “프로토콜을 시작해 줘.” | 1단계를 읽어 준다 |
| “현재 단계를 알려 줘.” | 현재 단계 재안내 (상태 불변) |
| “다시 말해 줘.” | 마지막 안내 1회 반복 |
| “다음 단계 미리 알려 줘.” | 다음 단계 미리보기 · 현재 단계가 게이트 중이면 “이 미리보기는 진입 승인이 아닙니다” 를 덧붙인다 |
| “다음 단계로 넘어가 줘.” | 완료 확인을 되묻는다 (그 자체로는 이동 없음) |

## 5. 7단계에서 게이트를 만난다

- 사용자: “현재 단계를 완료했어요”
- 에이전트:
  > 원문은 이 단계의 종점을 이렇게 적고 있습니다: “7 Repeat steps 2-7 until the
  > gel band is fully destained” 그 관찰 결과를 말씀해 주셔야 완료를 기록할 수
  > 있어요.
- 화면: `clarify_completion`, `current_step_label` 은 `7` 그대로, `revision` 불변.
- “이 단계의 완료 조건은 뭐야?” 라고 물으면 문서의 확인 기준을 읽어 준 뒤
  “이 단계는 관찰 결과가 충족될 때까지 반복하는 단계입니다 … 그 관찰 결과를
  말씀하기 전에는 이 단계를 완료 처리하지 마세요” 로 끝난다.

게이트가 서는 자리는 라벨이 아니라 **문서가 반복을 진술한 자리**다(in-gel 3곳,
headspace 5곳, intracellular·ANKOM 0곳). 17–18 반복 문장은 8쪽 20단계 본문에
있으므로 게이트는 18단계가 아니라 **20단계**에 선다.

## 6. 관찰을 말하고 전진한다

**종점에 도달했을 때**

- 사용자: “젤이 완전히 탈색되어 투명해요” (또는 되묻기에 “네”)
- 에이전트: “8단계로 이동했습니다. 안내를 화면에 표시했습니다. 타이머를
  시작하려면 말씀해주세요.”
- 기록: 프로토콜 id, 리비전 id, step id/라벨, **발화 원문**, UTC 시각, 선언자
  (principal id·역할), predicate `positive`. **반복 횟수는 기록하지 않는다.**
- 실험 세션 기록이 열려 있으면 같은 턴에 append-only `experiment_observations`
  행으로도 남는다. **그 기록이 없으면 전진이 되돌려진다.**

**아직 도달하지 않았을 때**

- 사용자: “아직 색이 남아 있어요” (또는 “아니요”)
- 에이전트:
  > 말씀한 결과는 7단계의 원문 관찰 기준이 아직 충족되지 않았다는 뜻입니다.
  > 현재 단계를 유지하며 다음 단계로 이동하지 않습니다. 원문이 지시한
  > 2–7단계 반복 주기를 계속한 뒤 관찰 결과를 다시 말씀해 주세요.

## 실패하면 확인할 3가지

1. **드롭다운 항목이 회색이다** → 2단계가 끝나지 않았다. 두 줄 모두 `· 확인됨`
   인지, 그리고 **`protocol_id` 가 `candidate-a-curated-development-v1` 인 항목에서**
   눌렀는지 확인한다. `protocol-…` 항목에서 눌렀다면 fixture 는 그대로다(0절).
   선언 직후라면 새 analysis 리비전에 다시 해소해야 한다.
2. **7단계에서 “네”라고 했는데 이동하지 않는다** → 되묻기는 **직전 턴 1회만**
   유효하다(turn_id · generation · configuration_id · workflow revision 전부 일치).
   중간에 다른 발화가 끼면 무효가 되어 완료를 다시 말해야 한다. 그리고
   `실험 세션 기록이 활성화되지 않아 관찰 내용을 저장하지 못했습니다.` 가 나오면
   기록이 열려 있지 않은 것이고, 이동은 되돌려진다.
3. **에이전트가 원문 대신 일반 문장으로 되묻는다**
   (`이 단계는 관찰 결과가 충족될 때까지 반복하는 단계입니다`) → 그 단계에 붙은
   반복 construct 를 찾지 못했다는 뜻이다. 분석이 반복을 포착하지 못한 경우이며
   `source_states_an_uncaptured_repetition` 이 함께 떠 있는지 확인한다. 문구를
   지어내지 않고 일반 문장으로 내려가는 것이 정상 동작이다.
