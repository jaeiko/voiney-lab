# 같은 과업으로 비교하는 파일럿 시험

목표는 준비·확인·재질문 비용까지 포함해 연구자의 수고가 줄어드는지 확인하는 것이다.
기존 문서·타이머·노트 방식, VoineyLab, 비교할 범용 음성 서비스를 같은 과업으로
시험한다. 제품별 기능은 시험하는 앱에서 먼저 확인하고 버전·설정을 기록한다.
완료한 결과만 결과로 보고하고, 아래 양식은 측정 결과로 제시하지 않는다.

## 1. 준비

- 첫 비교는 실험 재료를 사용하지 않는 모의 벤치에서 한다. 모든 비교 제품에 보낼 수
  있는 공개 자료를 쓰고, 같은 원문과 실행 버전을 사용한다. 기준 답은 연구자가 원문과
  대조해 미리 적는다. 원문에 없는 수치·절차·안전 주의는 시험자가 보충하지 않는다.
- 실제 태블릿과 사용할 브라우저에서 HTTPS·마이크 권한·음성 재생·화면 켜 두기·재연결을
  확인한다. 허용 마이크·출력 장치는 연구실과 확인한다. 화면 폭을 바꾼 CI 시험은 이
  기기 시험을 대신하지 않는다. 운영 순서는 [파일럿 안내](PILOT_GUIDE.md)와
  [HTTPS 안내](PILOT_HTTPS_SETUP.md)를 따른다.
- 같은 사람이 같은 과업을 시험하되 제품 순서를 바꾸어 학습 효과를 줄인다. 첫 등록과
  같은 문서를 다시 사용하는 경우를 구분한다. 준비 시간은 실험 진행 시간과 따로 잰다.
- 범용 서비스에는 기본 사용 조건과 충분한 지침을 준 조건을 구분한다. 지침 예:
  “첨부한 버전을 근거로 현재 단계의 조건을 알려 주세요. 질문만으로 단계를 완료하지
  말고, 원문에 없으면 없다고 말해 주세요. 관찰과 정정을 구분해 기록해 주세요.”

## 2. 과업과 미리 정할 판정

| 코드 | 할 일 | 확인할 결과 |
|---|---|---|
| SOURCE | 현재 단계의 조건을 묻는다 | 선택한 버전·단계의 원문 값과 단위가 맞고, 근거를 찾을 수 있다 |
| QUESTION | 다음 단계가 무엇인지 묻고 현재 위치를 다시 묻는다 | 조회만으로 완료·단계 위치·열린 확인 질문이 바뀌지 않는다 |
| TIMER | 원문의 타이머를 시작하고 다른 질문 뒤 남은 시간을 묻는다 | 실제 경과 시간과 맞고, 다른 질문이 타이머를 새로 시작하지 않는다 |
| RECORD | ‘테스트 메모 A’를 기록한 뒤 ‘테스트 메모 B’로 정정한다 | 테스트 기록과 정정을 구분해 다시 확인하고 노트로 옮길 수 있다 |
| RESUME | 안내를 중단하고 다른 질문 뒤 다시 이어간다 | 같은 진행 위치로 돌아오며, 하지 않은 단계를 완료했다고 기록하지 않는다 |

타이머·일시정지의 판정은 각 제품이 실제로 제공하는 동작을 먼저 적는다. 일시정지가
실험 반응 자체를 멈춘다는 가정은 하지 않는다. 제공하지 않는 기능과 실패한 기능도
구분해 기록한다. 특정 제품의 실패만 선별하지 않고 모든 결과를 남긴다.

## 3. 기록 양식

[빈 CSV 양식](../data/fixtures/evaluation/pilot_comparison_template.csv)을 복사해 사용한다.
한 행은 한 제품·한 설정·한 과업·한 반복이다. 실제 결과 파일은 저장소 밖에 보관한다.
연락처·이름·원음·전사·원문 문장·비공개 주소는 이 양식에 넣지 않는다.

| 열 | 적는 것 |
|---|---|
| `run_code`, `case_code`, `repeat_index` | 시험 구분 코드, 위 과업 코드, 반복 순서 |
| `product_code`, `configuration_code`, `app_version_code` | 비교 제품, 기본/지침/Voiney 설정의 구분, 실제 앱·빌드 버전 코드 |
| `source_case_code`, `source_revision_code` | 동일 원문·버전임을 확인할 시험용 코드 |
| `task_outcome_code` | `pass`, `fail`, `unsupported`, `not_tested` 중 실제 결과 |
| `setup_seconds`, `active_seconds` | 등록·분석·사람 확인 시간, 과업을 처리하는 시간. 반복 기록에서 준비 시간을 중복 합산하지 않는다 |
| `touch_count`, `reask_count` | 화면을 조작한 횟수, 인식·응답 문제로 다시 말한 횟수 |
| `wrong_state_change_count` | 미리 정한 기대와 다른 단계·완료·기록·타이머 변경 횟수 |
| `end_of_speech_to_audio_ms` | 사람이 말을 끝낸 순간부터 첫 소리가 들릴 때까지. 서버의 endpoint 이후 `first_audio_ms`와 섞지 않는다 |
| `issue_code` | 문제 구분 코드. 예: `source`, `speech`, `network`, `provider`, `recovery` |

응답이 없으면 음성 지연을 0으로 쓰지 않는다. 빈칸으로 두고 실패·원인을 기록한다.
네트워크·공급자 실패도 전체 시도 수에 포함하고 원인별로 함께 보고한다. 완료 시간은
성공한 시도 수를 함께 적고, 오류 때문에 포기한 시도가 빠지지 않도록 한다.

## 4. 분석 결과 비교

분석 모델의 저장된 JSON 두 개가 있으면, 같은 PDF에 대해 원문 근거 검사와 추출 차이를
따로 볼 수 있다. 아래 파일 이름은 시험자가 준비하는 입력이다.

```bash
python scripts/score_extraction.py source.pdf \
  --reference reference.json --candidate candidate.json --output comparison.json
```

JSON은 현재 분석 응답 형식(`analysis_schema_version`, `pdf_sha256`,
`capability_policy_id`, `protocol`)이다. 원문 체크섬이 다른 분석이나 깨진 입력은
비교하지 않는다. `--output`은 기존 파일을 덮어쓰지 않는다. 모델 호출과 카탈로그 쓰기는
없고, 분석이 실행 가능한지 판정하지도 않는다.

기준이 불완전하면 기준에만 없는 항목이 후보의 오류라는 뜻은 아니다. 번호가 없거나
겹치는 단계는 쪽·정확한 원문 인용으로 비교하므로 인용 범위가 다르면 양쪽 차이로
남는다. 구조 항목 비교는 근거 있는 내용의 포함 여부를 보여 주며 조건·의존 관계의
의미가 맞는지까지 판정하지 않는다. 상세 한계는
[평가 전략](../.agent/testing_strategy.md) 3절을 따른다.

## 5. 다음 개발을 고를 때

첫 사용과 재사용의 준비 시간을 포함해 조회·확인·기록에 드는 수고를 비교한다.
잘못된 상태 변경이 관찰되면 원인과 재현 조건부터 고친다. 오류가 관찰되지 않은
작은 시험을 안전성 보증으로 제시하지 않는다. 두 번째 사용에서도 도움 없이 같은
과업을 끝낼 수 있는지 확인하고, 차이가 작으면 다음 기능보다 초기 설정·확인 부담을
먼저 줄인다.
